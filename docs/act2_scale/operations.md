# Операции над данными

В соответствии с архитектурой необходимо разработать операции над хранимыми данными, которые позволят сохранить согласованность хранимых данных.

Общие правила:
- все изменения Cassandra `chat_members` и `private_chats` выполняются только через LWT, смешивание LWT и обычных записей над одними данными не допускается;
- операции идемпотентны: при повторе после сбоя они доводят до конца шаги, выполненные не полностью, вместо завершения с ошибкой.

### 1. Проверка прав пользователя отправить сообщение

Входные данные:
- ID отправителя (senderId);
- ID чата (chatId).

Результат:
- право отправки (canSend).

**Алгоритм:**

1. Выполнить выборку в Cassandra `chat_members` по `(chatId, senderId)`;
2. Если запись не найдена или чат удален (`deleted` = `true`), `canSend` ложно;
3. Иначе, `canSend` истинно.

### 2. Отправка сообщения

Входные данные:
- контент (content);
- ID отправителя (senderId);
- ID чата (chatId);
- ID сообщения клиентский (clientMessageId).

Результат:
- ID сообщения Snowflake (messageId);
- время отправки (sentAt).

**Алгоритм:**

1. [Проверка возможности пользователя писать в чат](#1-проверка-прав-пользователя-отправить-сообщение). При отсутствии возможности - завершение.
2. Сформировать ключ идемпотентности `msgKey` = `"msg:{chatId}:{senderId}:{clientMessageId}"`.
3. Сформировать Snowflake ID сообщения `messageId`.
4. Выполнить в Redis попытку установки `msgKey`: `messageId` с инструкциями NX и TTL окна идемпотентности.
5. Неудача (повторный запрос) => заменить `messageId` на значение из Redis.
6. Вычислить из времени, закодированного в `messageId`:
   - время отправки `sentAt`;
   - номер бакета `bucket`.
7. Неудача => прочитать сообщение из Cassandra `messages` по `(chatId, bucket, messageId)`.
8. Успех или сообщение не найдено на шаге 7 => выполнить вставку `(chatId, bucket)` в Cassandra `message_buckets`, затем вставку сообщения в Cassandra `messages` по `(chatId, bucket, messageId)`. Сообщение найдено => пропустить вставки.
9. Бакет вставляется до сообщения, поэтому сохраненное сообщение всегда видно при загрузке истории.
10. Обновить Cassandra `chat_activity` для `chatId` с меткой времени записи `USING TIMESTAMP`, равной `sentAt`.
11. Опубликовать в pub/sub событие о новом сообщении в чате `chatId`.
12. Опубликовать в JetStream событие для асинхронной индексации сообщения в OpenSearch.
13. Вернуть `messageId` и `sentAt`.

### 3. Создание личного чата

Входные данные:
- ID инициатора (userId);
- ID собеседника (peerId).

Результат:
- ID чата (chatId).

**Алгоритм:**

1. `userId` = `peerId` => завершение.
2. Выполнить выборку в PostgreSQL `users` по `peerId`. Пользователь не найден или заблокирован (`suspended` = `true`) => завершение.
3. Упорядочить пару: `userA` = min(`userId`, `peerId`), `userB` = max(`userId`, `peerId`).
4. Сформировать Snowflake ID чата `chatId`.
5. Выполнить в Cassandra `private_chats` вставку `(userA, userB, chatId)` при условии отсутствия записи (LWT).
6. Неудача => заменить `chatId` на значение из `private_chats` и прочитать чат из `chat_members`:
   - чат существует и не удален => перейти к шагу 8 (повтор после сбоя);
   - чат удален => удалить запись `private_chats` при условии совпадения `chat_id` (LWT), повторить с шага 4;
   - чат не найден => перейти к шагу 7.
7. Выполнить вставку в Cassandra `chat_members` одним batch по партиции `chatId` при условии отсутствия записей (LWT): строки `userA` и `userB`, `type` = `private`, `user_a`, `user_b`, `deleted` = `false`, `version` = `1`, `joined_at` = время из `chatId`. Неудача (чат создан параллельным запросом) => чат удален - повторить с шага 4, иначе продолжить.
8. Выполнить вставку `(userA, chatId)` и `(userB, chatId)` в Cassandra `user_chats`.
9. Опубликовать в pub/sub событие о создании чата `chatId`.
10. Вернуть `chatId`.

### 4. Создание группового чата

Входные данные:
- ID создателя (userId);
- название (title);
- ID участников (memberIds);
- ID запроса клиентский (clientRequestId).

Результат:
- ID чата (chatId).

**Алгоритм:**

1. `memberIds` содержит повторы, `userId` или более 100 элементов => завершение.
2. Выполнить выборку в PostgreSQL `users` по `memberIds`. Найдены не все или есть заблокированные => завершение.
3. Сформировать ключ идемпотентности `chatKey` = `"chat:{userId}:{clientRequestId}"`.
4. Сформировать Snowflake ID чата `chatId`.
5. Выполнить в Redis попытку установки `chatKey`: `chatId` с инструкциями NX и TTL окна идемпотентности. Неудача (повторный запрос) => заменить `chatId` на значение из Redis.
6. Выполнить вставку в Cassandra `chat_members` одним batch по партиции `chatId` при условии отсутствия записей (LWT): строки `userId` и `memberIds`, `type` = `group`, `title`, `admin_id` = `userId`, `deleted` = `false`, `version` = `1`, `joined_at` = время из `chatId`.
7. Успех => участники `members` = `userId` и `memberIds`. Неудача (чат создан предыдущей попыткой) => выполнить выборку участников из Cassandra `chat_members` по `chatId`: чат удален => вернуть `chatId`, завершение; иначе `members` = текущие участники.
8. Выполнить вставку `(memberId, chatId)` в Cassandra `user_chats` для каждого из `members`.
9. Опубликовать в pub/sub событие о создании чата `chatId`.
10. Вернуть `chatId`.

### 5. Добавление участника в чат

Входные данные:
- ID инициатора (initiatorId);
- ID чата (chatId);
- ID добавляемого пользователя (userId).

Результат:
- факт добавления.

**Алгоритм:**

1. Выполнить выборку в Cassandra `chat_members` по `(chatId, initiatorId)`. Запись не найдена или чат удален => завершение.
2. `type` != `group` или `admin_id` != `initiatorId` => завершение.
3. Выполнить выборку в PostgreSQL `users` по `userId`. Пользователь не найден или заблокирован => завершение.
4. Выполнить выборку в Cassandra `chat_members` по `(chatId, userId)`. Запись найдена => перейти к шагу 6 (повтор после сбоя).
5. Выполнить в Cassandra `chat_members` обновление (UPDATE) строки `(chatId, userId)`: `joined_at` = текущее время, увеличение `version` при условии совпадения `version` с прочитанной на шаге 1 (LWT). Неудача => повторить с шага 1.
6. Выполнить вставку `(userId, chatId)` в Cassandra `user_chats`.
7. Опубликовать в pub/sub событие о добавлении участника в чат `chatId`.

### 6. Удаление участника из чата

Удаление инициатором самого себя - выход из чата.

Входные данные:
- ID инициатора (initiatorId);
- ID чата (chatId);
- ID удаляемого участника (userId).

Результат:
- факт удаления.

**Алгоритм:**

1. Выполнить выборку в Cassandra `chat_members` по `(chatId, initiatorId)`. Запись не найдена или чат удален => `userId` = `initiatorId` - выполнить удаление `(userId, chatId)` из Cassandra `user_chats` (повтор выхода после сбоя); завершение.
2. `type` != `group` или `userId` = `admin_id` => завершение.
3. `userId` != `initiatorId` и `initiatorId` != `admin_id` => завершение.
4. Выполнить выборку в Cassandra `chat_members` по `(chatId, userId)`. Запись не найдена => выполнить удаление `(userId, chatId)` из Cassandra `user_chats` (повтор после сбоя); завершение.
5. Выполнить в Cassandra `chat_members` удаление `(chatId, userId)` с увеличением `version` при условии совпадения `version` с прочитанной на шаге 1 (LWT). Неудача => повторить с шага 1.
6. Выполнить удаление `(userId, chatId)` из Cassandra `user_chats`.
7. Опубликовать в pub/sub событие об удалении участника из чата `chatId`.

### 7. Выход администратора из группового чата

Входные данные:
- ID администратора (userId);
- ID чата (chatId).

Результат:
- факт выхода.

**Алгоритм:**

1. Выполнить выборку в Cassandra `chat_members` по `(chatId, userId)`. Запись не найдена или чат удален => выполнить удаление `(userId, chatId)` из Cassandra `user_chats` (повтор после сбоя); завершение.
2. `type` != `group` или `admin_id` != `userId` => завершение.
3. Выполнить выборку участников чата из Cassandra `chat_members` по `chatId` и выбрать среди них, кроме `userId`, преемника `successorId`.
4. Выполнить в Cassandra `chat_members` при условии совпадения `version` с прочитанной на шаге 1 (LWT):
   - удаление `(chatId, userId)`;
   - преемник найден => `admin_id` = `successorId`, иначе `deleted` = `true`;
   - увеличение `version`.
5. Неудача => повторить с шага 1.
6. Выполнить удаление `(userId, chatId)` из Cassandra `user_chats`.
7. Опубликовать в pub/sub событие о выходе участника из чата `chatId`.

### 8. Удаление чата

Входные данные:
- ID инициатора (initiatorId);
- ID чата (chatId).

Результат:
- факт удаления.

**Алгоритм:**

1. Выполнить выборку в Cassandra `chat_members` по `(chatId, initiatorId)`. Запись не найдена => завершение.
2. `type` = `group` и `admin_id` != `initiatorId` => завершение.
3. Чат удален => перейти к шагу 4 (повтор после сбоя). Иначе выполнить в Cassandra `chat_members` установку `deleted` = `true` с увеличением `version` при условии совпадения `version` с прочитанной на шаге 1 (LWT). Неудача => повторить с шага 1.
4. `type` = `private` => удалить `(user_a, user_b)` из Cassandra `private_chats` при условии совпадения `chat_id` с `chatId` (LWT).
5. Выполнить выборку участников чата из Cassandra `chat_members` по `chatId` и удалить `(memberId, chatId)` из `user_chats` для каждого.
6. Опубликовать в pub/sub событие об удалении чата `chatId`.

### 9. Получение списка чатов пользователя

Входные данные:
- ID пользователя (userId).

Результат:
- список чатов (chats).

**Алгоритм:**

1. Выполнить выборку в Cassandra `user_chats` по `userId`.
2. Для каждого `chatId` параллельно выполнить выборку данных чата из `chat_members` и последнего сообщения из `chat_activity`.
3. Отбросить удаленные чаты.
4. Отсортировать чаты по `last_message_id`, при его отсутствии - по `chatId`, по убыванию.
5. Вернуть `chats`.

### 10. Получение чата

Входные данные:
- ID пользователя (userId);
- ID чата (chatId).

Результат:
- данные чата (chat).

**Алгоритм:**

1. Выполнить выборку в Cassandra `chat_members` по `(chatId, userId)`. Запись не найдена или чат удален => завершение.
2. Выполнить выборку последнего сообщения из Cassandra `chat_activity` по `chatId`.
3. Вернуть `chat`.

### 11. Получение участников чата

Входные данные:
- ID пользователя (userId);
- ID чата (chatId).

Результат:
- список участников (members).

**Алгоритм:**

1. [Проверка прав пользователя](#1-проверка-прав-пользователя-отправить-сообщение). При отсутствии прав - завершение.
2. Выполнить выборку в Cassandra `chat_members` по `chatId`.
3. Вернуть `user_id` и `joined_at` участников.

### 12. Загрузка истории сообщений

Входные данные:
- ID пользователя (userId);
- ID чата (chatId);
- ID сообщения, до которого (before) или после которого (after) выполняется загрузка;
- количество сообщений (limit).

Результат:
- список сообщений (messages).

**Алгоритм:**

1. [Проверка прав пользователя](#1-проверка-прав-пользователя-отправить-сообщение). При отсутствии прав - завершение.
2. Вычислить номер бакета `bucket` из времени, закодированного в `before` или `after`.
3. Выполнить выборку бакетов чата из Cassandra `message_buckets` по `chatId`:
   - `before` => бакеты <= `bucket` по убыванию;
   - `after` => бакеты >= `bucket` по возрастанию.
4. Последовательно по бакетам выполнять выборку из Cassandra `messages` по `(chatId, bucket)`, пока не набрано `limit` сообщений:
   - `before` => `message_id` < `before` по убыванию;
   - `after` => `message_id` > `after` по возрастанию.
5. Вернуть `messages`.

### 13. Поиск сообщений в чате

Входные данные:
- ID пользователя (userId);
- ID чата (chatId);
- строка поиска (q);
- ID сообщения, до которого выполняется поиск (before);
- количество сообщений (limit).

Результат:
- список сообщений (messages).

**Алгоритм:**

1. [Проверка прав пользователя](#1-проверка-прав-пользователя-отправить-сообщение). При отсутствии прав - завершение.
2. Выполнить поиск в OpenSearch по `q` с фильтрами `chat_id` = `chatId`, `message_id` < `before`, без удаленных, по убыванию `message_id`, не более `limit`.
3. Вернуть `messages`.

### 14. Регистрация пользователя

Входные данные:
- логин (login);
- пароль (password).

Результат:
- ID пользователя (userId).

**Алгоритм:**

1. Сформировать хеш пароля `passwordHash` (argon2id).
2. Сформировать UUID пользователя `userId`.
3. Выполнить вставку в PostgreSQL `users`. Конфликт по `login` => завершение.
4. Вернуть `userId`.

### 18. Создание сессии

Входные данные:
- логин (login);
- пароль (password).

Результат:
- ID сессии (sessionId);
- токен доступа (token);
- токен обновления (refreshToken).

**Алгоритм:**

1. Выполнить выборку в PostgreSQL `users` по `login`. Пользователь не найден или заблокирован => завершение.
2. Проверить `password` по `password_hash`. Не совпадает => завершение.
3. Сформировать UUID сессии `sessionId`, случайный `secret` и `refreshToken` = `"{userId}.{sessionId}.{secret}"`.
4. Выполнить вставку в PostgreSQL `sessions` с хешем `secret` и `expires_at`.
5. Сформировать `token`.
6. Вернуть `sessionId`, `token` и `refreshToken`.

### 19. Обновление токена

Входные данные:
- токен обновления (refreshToken).

Результат:
- токен доступа (token);
- токен обновления (refreshToken).

**Алгоритм:**

1. Разобрать `refreshToken` на `userId`, `sessionId` и `secret`. Неверный формат => завершение.
2. Сформировать новый `newSecret` и `newRefreshToken` = `"{userId}.{sessionId}.{newSecret}"`.
3. Выполнить обновление в PostgreSQL `sessions` по `(userId, sessionId)`: хеш `secret` заменить на хеш `newSecret`, продлить `expires_at` при условии совпадения хеша `secret`, что сессия не отозвана и не истекла. Запись не обновлена => завершение.
4. Сформировать `token`.
5. Вернуть `token` и `newRefreshToken`.

### 20. Отзыв сессии

Входные данные:
- ID пользователя (userId);
- ID сессии (sessionId).

Результат:
- факт отзыва.

**Алгоритм:**

1. Выполнить обновление в PostgreSQL `sessions` по `(sessionId, userId)`: `revoked_at` = текущее время при условии, что сессия не отозвана. Запись не обновлена => завершение.
2. Выполнить в Redis установку `"revoked:{sessionId}"` с TTL, равным времени жизни токена доступа.
3. Опубликовать в pub/sub событие об отзыве сессии `sessionId`.

### 21. Валидация сессии

Входные данные:
- токен доступа (token).

Результат:
- ID пользователя (userId);
- ID сессии (sessionId).

**Алгоритм:**

1. Проверить подпись и срок действия `token`. Невалиден => завершение.
2. Выполнить в Redis проверку наличия `"revoked:{sessionId}"`. Ключ найден => завершение.
3. Вернуть `userId` и `sessionId`.
