# Архитектура

Задача состоит в том, чтобы сделать мессенджер _горизонтально масштабируемым_.

Для этого необходимо перейти на другие системы хранения данных и переработать сервисы шлюза и мессенджера под работу в числе нескольких копий.

## Компоненты

**Балансировщик нагрузки**

**N инстансов сервиса мессенджера**<br/>
**M инстансов сервиса шлюза**<br/>
**K хостов хранилища сообщений**<br/>
**L хостов хранилища пользователей**<br/>
**P хостов in-memory хранилища**<br/>
**Q хостов pub/sub системы**<br/>
**R хостов поискового сервиса**<br/>

## Детализация

### Балансировщик нагрузки

**Задачи:** 
- проксирование соединений пользователей с инстансами мессенджера и шлюзами соединений с учетом их нагруженности;
- отслеживание состояний инстансов.

**Реализация:** HAProxy.

### Сервис мессенджера

**Задачи:**
- управление пользовательскими аккаунтами и сопутствующими данными;
- управление процессом пересылки сообщений;
- управление авторизацией: сессии, отзыв сессий, валидация сессий.

**Реализация:** микросервис _messenger_ на Golang.

### Сервис шлюза

**Задачи:**
- доставка сообщений и других событий пользователю, надодящемуся онлайн;
- учет статусов пользователей и специальных индикаторов (присутствие, набор текста, просмотр чата);
- передача от пользователя действий в сервис месснджера.

**Реализация:** микросервис _gateway_ на Golang.

### Хранилище сообщений

**Задачи:**
- хранение сообщений;
- хранение данных о чатах и их участниках;
- быстрое исполнение специфических запросов на добавление и получение данных.

**Реализация:** кластер Apache Cassandra.
Причина выбора - возможность горизонтального масштабирования и приспособленность для работы с большими данными.

### Хранилище пользователей

**Задачи:** 
- хранение пользователей;
- хранение сессий пользователей;
- хранение профилей пользователей.

**Реализация:** изначально PostgreSQL, далее кластер Citus.
Причина выбора - возможность наложения ограничений на данные, строгая согласованность и нормализованное хранение.

### In-memory хранилище

**Задачи:**
- хранение ID отправленных сообщений для идемпотентности отправки;
- хранение ID отозванных сессий;
- хранение информации о подключении пользователя к шлюзам.

**Реализация:** кластер Redis.
Причина выбора - быстрый доступ к данным за счет типа хранения key-value.

### Pub/sub система

**Задачи:** 
- передача событий между сервисами: сообщения (в групповые чаты), присутствие пользователей и другие события.

**Реализация:** NATS.
Причина выбора - наличие функционала подписчик-издатель и возможность горизонтального масштабирования.

### Поисковой сервис

**Задачи:**
- поиск пользователей;
- поиск сообщений;

**Реализация:** OpenSearch.
Причина выбора - возможность поиска по тексту и работы с большими данными.
