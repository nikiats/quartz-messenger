# Архитектурные решения

## Протоколы взаимодействия

**Р1. Клиент <-> шлюз**: `WebSocket`, в силу необходимости дуплексного обмена сообщениями в реальном времени.

**Р2. Клиент -> сервис мессенджера**: `HTTP`, в силу широкой поддержки, включая веб-браузеры и приложения для мобильных устройств.

**Р3. Шлюз -> сервис мессенджера**: `HTTP`, в силу простоты реализации и отладки.

**Р4. Сервис мессенджера -> шлюз**: `HTTP`, причины аналогичны описанным для **Р3**.

## Идентификаторы

**Пользователи, чаты, сессии**

Идентификаторы пользователей, чатов и сессий — `UUID`, генерируются сервисом мессенджера.
Выбор обусловлен тем, что последовательные целочисленные идентификаторы раскрывают данные о состоянии системы.

**Сообщения**

Сообщение идентифицируется чатом `chatId` и порядковым номером в этом чате `seqnum`.
Для этого устанавливается ограничение на уникальность пары `(chatId, seqnum)`.

## Авторизация сервисов

Сервисы передают статический токен в виде Bearer HTTP аутентификации.
Дополнительно к этой защите добавляется защита на уровне сети: внутренние ручки не доступны снаружи.

## Авторизация пользователя

**Получение токена**

Через сервис мессенджера пользователь получает два токена: токен авторизации и токен обновления (refresh).

Время жизни: `15` минут и `7` дней для токена и токена обновления соответственно.

Обновление токена выполняется в этом же сервисе.
Вместе с токенами передается ID сессии.

Сессия и хеш токена обновления хранятся в `PostgreSQL`. Хранится именно хеш:
утечка базы не должна давать возможности продлевать чужие сессии.

**Авторизация по токену**

В зависимости от того, с чем клиент взаимодействует, возможны 2 варианта:

Клиент -> Сервис мессенджера [HTTP Bearer]

Клиент -> Шлюз [Сообщение с токеном] -> Проверка токена в сервисе мессенджера [POST запрос]

**Отзыв сессии**

Для моментального отзыва сессии токен авторизации не является stateless.
При каждом запросе к сервису мессенджера, выполняется проверка того, был ли данный токен отозван. 

Возможны ситуации отзыва сессий:
- выход из аккаунта в клиентском приложении;
- деактивация аккаунта пользователя в системе;
- другие случаи.

В таком случае:
1. в базе данных инвалидируется токен обновления сессии;
2. в базу данных отозванных сессий записывается хеш токена, сессия которого отозвана (в MVP - в память сервиса мессенджера);
3. шлюзу соединений отправляется запрос на разрыв соединения с пользователем указанной сессии.

При приближении времени сессии к истечению (ближе, чем за 30 секунд), шлюз запрашивает у пользователя повторную авторизацию. При отсутствии сообщения авторизации, спустя это время сессия будет инвалидирована и шлюз закроет соединение.

## Процесс передачи сообщений

**Нумерация**

Сервер присваивает каждому сообщению порядковый номер в чате (`seqnum`) в момент отправки.
Нумерация непрерывна, каждый инкремент атомарен.
Это необходимо для того, чтобы клиент мог определить, какие сообщения пропущены для их подгрузки.

**Порядок отправки сообщения**

Основным вариантом отправки сообщения является отправка через WebSocket соединение.
Для этого перед отправкой сообщения устанавливается дуплексное соединение клиента с шлюзом соединений.
Далее порядок действий следующий:

1. клиент генерирует `clientMessageId` в формате UUID;
2. клиент формирует сообщение и посылает его в шлюз соединений;
3. шлюз передает сообщение в сервис мессенджера, получает ответ;
4. шлюз сообщает клиенту, что сообщение доставлено на сервер и передает присвоенный ему сервером `seqnum` и `sentAt`;
5. сервис мессенджера передает шлюзу сообщение с указанием выполнить доставку получателю (или получателям);
6. шлюз сообщает сервису мессенджера, что доставка взята в работу без уточнения ее статуса.

Доставка в режиме реального времени работает при наличии активного соединения клиента со шлюзом.

Отправка сообщения возможна по протоколу `HTTP` напрямую через сервис мессенджера. Данный вариант является резервным.
В этом случае подтверждение с `seqnum` и `sentAt` приходит ответом на запрос, а не отдельным
сообщением по соединению. Доставка получателям происходит одинаково в обоих случаях.

Клиент может определить, что сообщение пропущено, по `seqnum` и самостоятельно инициировать подгрузку.

Общая диаграмма есть в [сценариях](../implementation/scenarios.md).

**Поддержка соединения**

Каждые `60 секунд` шлюз соединений ожидает как минимум одно сообщение от клиента.
При отсутствии такового, соединение закрывается шлюзом.

Для выполнения этого требования предусмотрены `ping` пакеты, которые сообщают шлюзу, что клиент активен. Клиент направляет их за `10` секунд до наступления 60 секунд молчания.

Шлюз в ответ направляет `pong` пакет.

**Загрузка сообщений, не полученных через соединение**

Пользователь хранит информацию о максимальном `seqnum`, который был получен.

После установки подключения, выполняется подгрузка предыдущих сообщений по запросам клиента с пагинацией.

`seqnum` используется как для определения границ подгрузки, так и для упорядочивания новых пришедших и отправленных сообщений, в том числе в "спорных" ситуациях (например, 2 пользователя отправили несколько сообщений одновременно).

**Идемпотентность отправки**

Идемпотентность достигается за счет ограничения уникальности на пару `(senderId, clientMessageId)`.

Клиентский UUID сообщения сохраняется между повторными отправками.
Сервис мессенджера не отправляет несколько сообщений с одним клиентским ID => отправка не дублируется.

При отправке с конфликтом по `clientMessageId`, *возвращается успешный ответ с уже существующим `seqnum`*.

## Удаление сообщений

Строка сообщения не удаляется из базы данных, а отмечается удаленной.
Содержимое сообщения при удалении в базе данных сохраняется.

При выдаче сообщений клиенту на местах удаленных сообщений будут маркеры удаленных сообщений, чтобы сохранить сплошную нумерацию.
